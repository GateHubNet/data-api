## 1. Findings

Severity: MEDIUM = breaks a documented happy path or an operating budget, LOW = doc/contract mismatch, INFO = observation. Each gives the
request, what was expected and what happened.

### F1 (MEDIUM, docs/contract) `asset` / `asset2` with a raw `+` is 400 `issuer is required`

- Request: `GET /v2/amm/pools?asset=XRP&asset2=6D5442494C4C0000000000000000000000000000+rfmS3zqrQrka8wVyhXifEeyTwe8AMz2Yhw` (the shape of the example in
  `docs/api-reference.md`, "GET /v2/amm/pools": `asset=XRP&asset2=USD+rIssuer` is the XRP/USD pool; "the separators `+`, `|` and `.` all work").
- Expected: 200 with the pool. Actual: **400** `{"result":"error","message":"issuer is required"}`.
- Cause: in a URL query a raw `+` is a space, so the route gets `CUR rIssuer` and `asset-param.ts` (`raw.split(/[+|.]/)`) finds no separator. The same asset
  as `%2B` (`...%2BrfmS3...`), as `|` or as `.` is 200 (calls 012 to 014 and 016 of Appendix A; call 015 is the 400). The path routes (`/v2/amm/pools/{base}/{counter}`,
  `/v2/exchanges/{base}/{counter}`) are not affected, `+` is literal in a path. Either the docs example must write `%2B` or the parser must split on a space too.

### F2 (INFO, data shape) a short window leaves most pools without `lp_supply`, `trading_fee` and `lp_currency`, and the fee estimates read 0

- After the first 300 ledgers 5 of 216 pools had `lp_supply` and `trading_fee`, after 987 ledgers **only 18 of 463**: a swap says nothing of either, so a pool serves them only when a
  create, deposit, withdraw or vote of the window carried them (`amm_pools` rows: 463, `lp_supply` 18, `trading_fee` 18, `value_native` 392, `created_ledger` 2).
  This is the documented behaviour ("a key whose value is unknown is left out"); the node's `amm_info` has all of them for every pool (section 7).
- Consequence in `amm_daily`: **461 of 473 pool-days with swaps have no fee known, and their `fees_base_est` / `fees_counter_est` are the string `"0"`**, not left out
  (`docs/api-reference.md`: "each swap's input times the pool's trading fee"; the job's comment says a swap with no fee "adds its volume and no fee").
  A reader cannot tell a fee of 0 from an unknown fee, and `GET /v2/amm/pools/{pool}/history?interval=day` has `trading_fee` out and `fees_*_est: "0"` in the same row (call 031: 93 swaps, no `trading_fee`, `fees_base_est` `"0"`).
  A database that has not been re-ingested from the AMM enablement ledger (86795265) shows the same (docs/backfill.md covers the re-ingest, not this effect on the estimates).
- Same cause: an IOU/IOU pool whose second reserve line was not seen has `reserve_counter` out (`raMjX...`, `rsCJZ...`), correct as far as it goes; the node has it.

### F3 (MEDIUM, operability) `amm_daily` grows to its whole 4 s budget at about 450 pools, and the budget is only checked between days

- The `amm_daily` run for today (every 5th tick) took, with the pools touched so far: 216 pools 1,771 ms, 310 pools 2,594 ms, 387 pools 3,135 ms, 439 pools 3,778 ms,
  447 pools plus 33 pools of a second day 3,959 ms: **about 8.5 ms per pool-day, linear**, and it ended 41 ms under `AGGREGATOR_AMM_DAILY_BUDGET_MS` (4,000) with 1 hour of mainnet traffic.
  The budget is not enforced inside a day ("a day is never cut"), so there is no warning; a day with 1,000 to 2,000 pools (a guess from 447 pools in the first hour, not measured) would be 8 to 17 s per run,
  and the same tick (30 s budget) also runs `stats_dirty` (5.9 s tick wall in the last tick: `stats_dirty` 0.99 s + `amm_daily` 3.96 s).
  The set for today is rewritten whole every 5th tick, so the cost of each run grows through the day. `amm_pools` is cheaper (1.67 s for the first 216 pools, then 3 ms idle, median 222 ms and max 873 ms live).
  Needs a decision before mainnet-size use (incremental sets, or a budget that is honoured per chunk of pools).

### F4 (MEDIUM, environment) `wss://s2.ripple.com` throttles the modest verifier, and three docs say it does not

- 07:54:34 and 07:54:52 UTC: `range-ingest --concurrency 2` (2 requests in flight, about 4 per second) was refused after about 25 requests, twice (`slowDown`: `You are placing too much load on the server.`,
  the NodeClient paused the endpoint for 10 s each time). Stopped at once (rule), 19 ledgers committed.
- 08:37:19 UTC: again, through my own throttling proxy (one request in flight, about 1.8 requests per second from the live syncer and a range ingest together; the refused request was a keep-alive `ping`, the 896th of the second proxy).
  Everything was stopped by the watchdog (rule). 1,336 requests had been made through the two proxy instances by then (1,003 `ledger`, 217 `ping`, 38 `amm_info`, 31 `server_info`, 15 `tx`, 13 `ledger_entry`, 11 `account_info`, 6 `account_lines`, 2 others),
  plus about 28 direct ones (the first attempt and a few `rpc.js` calls).
- Between the two, the proxy at one request in flight (about 2 per second for the range ingest, 1 per second for the live syncer) made 1,335 requests in 34 minutes without a refusal. `docs/configuration.md` (`GH_CATCHUP_CONCURRENCY`), `docs/backfill.md` ("Throughput", concurrency 2 "is fine") and `docs/syncer.md` ("it did not throttle a first sync") say "`wss://s2.ripple.com` did not throttle a first sync at 2",
  true on 2026-10-16 and was not true today at the same concurrency; a first run needs the pacing the docs do not give (the node is a Clio 2.8.0 server).
- The `range-ingest` CLI has no rate option except `--concurrency`; one in flight is still about 2 requests per second.

### F5 (INFO) `syncer_amm_unclassified_total` has no trace in a `range-ingest` run unless it is above 0

- `docs/backfill.md` ("the range-ingest log names the total of its run"): the CLI logs a warning only when the total is above 0, and its Prometheus counter dies with the process.
  A clean run therefore proves a 0 only by the absence of a line. The live syncer exposes it (`syncer_amm_unclassified_total 0` on `/metricz`).

### F6 (INFO) CSV of an empty list is an empty body, with no header row

- `GET /v2/amm/pools/{pool}/governance?format=csv` of a pool with no vote or bid: 200, `Content-Length: 0` (the same as `/v2/payments`, `/v2/exchanges` and every older list).
  The docs say the AMM CSVs "have the same columns on every page"; an empty list has no page. With a row (the vote of call 062) the 16-column header is exact.

### F7 (INFO) Checks that could not exercise a documented path

- R-A10 transfer fee on the paid-out asset: no issuer with a `TransferRate` among the 11 checked (the 8 busiest swapped issuers and the issuers of the 5 compared swaps all answer none on `account_info`), so the compared pool deltas
  (which equal the node by construction) do not show the fee branch. `docs/operations.md` "`AMM daily back-fill: N days to compute`": never printed, there was no closed day to owe before the first tick (the line is announced only when days are owed).
- No AMMBid in 987 ledgers, one AMMVote (`rEP6dd9aVaw...`, ledger 107735854), so the `bid` object of the governance route was not served live.

### F8 (INFO) Method notes (not product defects)

- Clio's `account_lines` with `peer` is a paged search and answered an empty page with a `marker` for an account with more than 400 lines; the LP-token line is read by its ledger entry index instead (`xrpl.hashes.hashTrustline`).
- `ledger_entry` with `ripple_state.accounts` answered `malformedAddresses` for pool pseudo-accounts on this server; the index form works.
- A pool's `amm_info` at `ledger_index = last_ledger` is the right comparison point: nothing but the pool's own transactions changes its fields.
