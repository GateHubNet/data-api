# MPTokens (D9) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Index MPTokensV1 issuances, holders and transfers (clawbacks, locks and MPT escrows included), serve them at `/v2/mpt/{issuanceId}` (`/holders`, `/transfers`), `GET /v2/mpt?ids=`, `/v2/accounts/{address}/mpt` and `kind=mpt` on D6's `/v2/tokens`, and stop dropping MPT payments from `payments` and `balance_changes`.

**Architecture:** One additive migration adds five ledger tables, written by `LedgerWriter` from a new pure `MptParser` (shared delta reader `mptDeltas`), and two aggregates rebuilt by a new aggregator job `mpt_state` that follows the `amm_pools` runner. The payment and balance-change parsers learn MPT amounts; the new gate `MPT_PARSER_VERSION` marks the ledgers that hold the rows. A new API module `apps/api/src/mpt/` serves the issuance, its holders and transfers, the `?ids=` batch and the MPT kind of the token list, with D3's `FeatureCoverageService` for `coverage`; the account holdings route joins `AccountsModule`.

**Tech Stack:** TypeScript (strict), NestJS 10, ClickHouse 26.8 (`@clickhouse/client`), pnpm 10 workspace, jest + ts-jest, testcontainers, supertest, `bignumber.js`, `ripple-address-codec` (already a dependency of `packages/shared`), Node's `TextDecoder` (`fatal: true`).

**Spec:** `docs/superpowers/specs/2026-10-17-mpt-data-design.md` (revised 2026-10-24; cited as "spec §n" and "decision n"). The plan argues from the spec; executors read both. This file replaces the plan written for the 2026-10-17 version, which was never executed.

**Branch:** `feat/explorer-data-2` in `/Users/golobitch/github.com/GateHubNet/data-api-worktrees/explorer-data-2` (stacked on the owner's PR #20). D9 is the last data API sub-project: before Task 1, D-env and D3–D8 are built and committed on this branch. Nothing is pushed.

Narrow runs: `… test -- <pattern>`.
- **Commits:** Conventional Commits (`feat(shared): …`, `feat(syncer): …`, `feat(api): …`, `test: …`, `docs: …`), a body saying why, the trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never `--amend`, never `git add -A` or `git add .` (name the files), never touch `.claude/`, never push.
- **Repo conventions** (`docs/development.md` §5): table names only from `Table`; every user-derived value a bound parameter; no `FINAL`; key-ordered reads; exact amounts (`BigInt` for MPT integer units, `BigNumber` elsewhere), never a float in a served figure; config only through the config classes; everything new of `packages/shared` exported from `packages/shared/src/index.ts`.
- **UInt64 reads:** every `UInt64` column (`amount`, `escrowed_amount`, `outstanding_amount`, `maximum_amount`, `locked_amount`, `fee`, `version`) is selected as `toString(col)` (rows.ts: a `UInt64` read back as a number loses digits above 2^53).
- **Representation (spec §2):** an MPT is `currency` = the 48 upper-case hex digits of its issuance ID and `issuer` = the issuer decoded from the ID, in every `(currency, issuer)` column; 48 hex digits are always an MPT, 3-character and 40-hex codes stay issued currencies. MPT amounts are the ledger's integer units everywhere (strings in answers, `UInt64` in the MPT tables, `String` in the existing tables), never scaled. D5's MPT amount object is not changed; D9's own answers carry amounts as integer strings beside the issuance ID.
- **IDs on routes:** 48 hex digits in either case, answered in upper case; anything else 400 `invalid mpt issuance id`, checked before any other parameter. The route parameter is named `issuanceId` (`@Get(':issuanceId')`), so `docs/openapi.yaml` names the paths `/v2/mpt/{issuanceId}…`, as E14's client does.
- **Coverage (D3 §4):** the entry `mpt` of `COVERAGE_FEATURES` = `{ parserVersion: MPT_PARSER_VERSION, startOf: (p) => p.hasMpt ? { kind: 'amendment', amendment: 'MPTokensV1' } : { kind: 'unavailable' } }`; every answer's `coverage` is `FeatureCoverageService.coverage('mpt')` (on Xahau and Xahau Testnet that is `complete: true` with the service's `from_ledger_index`), and while `isAvailable('mpt')` is false the routes read no MPT table. `coverage` is the key right after `result`, never in the CSV. `?ids=` has none.
- **Reads:** every read of a ledger table is capped at the committed head (`committedHead`); aggregates are read newest version per key (`ORDER BY <key>, version DESC LIMIT 1 BY <key>`), never with `FINAL`.
- **Answers:** a key with no value is absent, never `null`; ledger times `YYYY-MM-DDTHH:mm:ssZ` (`fmtTime`); counts are numbers; key order is the exported `*_KEYS` constant, pinned by tests and by the "Keys of …, in order:" lines of `docs/api-reference.md`. `Cache-Control` is the global `private, max-age=60`.
- **Errors**, exactly, in the order each route lists them: 400 `invalid mpt issuance id`, `ids is required`, `too many ids`, `issuer does not match mpt issuance`, `invalid kind - use: issued, mpt`, `invalid kind - use: payment, clawback, lock, unlock, escrow_create, escrow_finish, escrow_cancel`, `invalid start date format`, `invalid end date format`, `invalid ripple address`, `invalid marker`; 404 `issuance not found`; 500 `unable to retrieve issuance`, `unable to retrieve issuances`, `unable to retrieve holders`, `unable to retrieve transfers`, `unable to retrieve tokens`, `unable to retrieve mpt holdings`.
- **Ripple parity:** the recorded and ripple-mock fixtures hold no MPT; every existing golden snapshot and parity test stays byte-identical (the one allowed change is named in Task 5).
- **Recording:** only from `wss://s2.ripple.com` (XRPL Testnet facts from `clio.altnet.rippletest.net:51234`), at most two requests in flight; stop on a rate-limit answer. Never hand-write data presented as recorded; a synthetic case says which recorded case it was edited from and how.
- **Metrics** are syncer-only, prefix `syncer_`; the API adds none.

Plan decisions (the spec leaves them open):
- `?ids=` answers one entry per ID asked, duplicates included, in request order; an empty element is `invalid mpt issuance id`.
- `kind=mpt` with nothing to list (no `mpt_issuances` row, or Xahau) is a `TokenListPage` with zero totals (`{ issuances: 0, holders: 0, transfers_24h: 0 }`, `total: 0`, no rows) at the newest committed ledger, so D6's full envelope; only with no committed ledger at all does `list` answer `undefined` (D6's no-generation answer).
- `locked_holders` and the per-holder part of `locked_amount` count balances above 0 (`amount + escrowed_amount > 0`), the same holders `holders` counts; `locked` of a holder row is its own `lsfMPTLocked` or the issuance's.
- The XLS-89 conformance check judges the decoded object, whichever keys (long, short, draft `urls`) spelled it.
- The `mpt_state` job runs on every network (on Xahau its tables are empty and each tick reads nothing).

## Review Focus

1. **A holder-to-holder payment with a transfer fee, and one recorded before fixMPTDeliveredAmount.** The delivered amount, the burned fee (`OutstandingAmount` falls by it), the transfer's `fee` and the four balance-change rows must agree, or the issuer's and holders' histories drift apart. Tests: Task 4 `records the burned fee of payment_transfer_fee` and `delivers Amount before the fix`; Task 5 `balances payment_transfer_fee`.
2. **Xahau and Xahau Testnet.** Every MPT route answers without reading an MPT table: `kind=mpt` an empty list with `complete: true`, `/v2/mpt/{id}` and its lists 404, `?ids=` bare IDs, `/accounts/{a}/mpt` empty with `complete: true`. Tests: Task 10 `answers Xahau without reading an MPT table`; Task 12 `answers kind=mpt on Xahau empty and complete`; Task 13 `answers holdings on Xahau empty and complete`.
3. **An issuance whose state is outside the coverage, or newer than the last tick.** It has holders but `state_known = 0`: `/v2/mpt/{id}` 404, the list leaves it out, its holders and transfers are still served (E14 shows the node beside them). Tests: Task 7 `writes state_known 0 for an issuance with holder rows only`; Task 10 `404s an issuance whose state is not known`; Task 11 `serves the holders and transfers of an issuance whose state is not known`.
4. **IDs and assets written another way.** Lower-case 48 hex accepted and upper-cased; 47 or 49 hex, `0x…`, an empty element of `ids` refused; `<48hex>+<another issuer>` 400 `issuer does not match mpt issuance`; a 40-hex currency still an issued one; 101 IDs `too many ids`. Tests: Task 2 `decodeMptIssuanceId`; Task 9 `parses the MPT asset syntax`; Task 10 `refuses ids in order`.
5. **Metadata an issuer wrote any way it liked.** Not UTF-8, not JSON, a JSON array, more than 1024 bytes, short keys, the draft `urls`, wrong types, 5,000-character strings: the hex is always served, `metadata` only when decoded, `metadata_conforms` false unless every XLS-89 rule holds, `ticker` cut to 16 and `name` to 128. Tests: Task 2 `mpt-metadata.spec.ts`; Task 7 `keeps the hex and no metadata for metadata that is not JSON`; Task 10 `serves metadata_hex without metadata`.

## Rulings

1. **Spec §4.3's second invariant, restated.** As worded ("the holders' `MPTAmount` changes plus the `OutstandingAmount` change sum to zero except for escrow moves and clawbacks") it fails on a payment with a transfer fee (holders −fee, outstanding −fee). The ledger's rule, which holds for every case including escrows and clawbacks, is tested instead: per transaction and issuance, Σ holders (ΔMPTAmount + ΔLockedAmount) = ΔOutstandingAmount, and 0 when the issuance node is not in the metadata (Task 4).
2. **Decision 8 ("every row of a `Clawback`")** is read as every balance row; the `transaction_cost` row of the fee keeps its type, as for every other transaction (Task 5).
3. **`asset_scale` above 19** (the ledger allows 0–255) is stored and served as it is; scaling is the explorer's (E14 shows it unscaled).
4. **Parameter name.** The MPT routes name their path parameter `issuanceId`, so the OpenAPI paths match E14's client (`/v2/mpt/{issuanceId}`); the spec's captions already use it.
5. **Numbers.** Migration `017`, `MPT_PARSER_VERSION = 10`, ADR `0020`, ADR-0010 Amendment 11 (consistency pass: the amendments run in build order, D8 taking 10), each checked at build time.
6. **One MPT ID module.** Spec §4 names `util/mpt-id.ts`; D5's plan already made `packages/shared/src/util/mpt.ts` with `isMptIssuanceId` and `mptIssuerOf` (the earlier sub-project defines), so D9 adds `mptIssuanceId` and `decodeMptIssuanceId` there instead of a second module with a clashing export.
7. **Seams of the earlier plans used as they built them:** coverage through D3's `COVERAGE_FEATURES` entry `mpt` (`startOf` → `amendment` / `unavailable`), and the list through D6's `TOKEN_KINDS` and `TOKEN_LIST_SERVICES` (`MptTokensService implements TokenListService`), not a coverage wrapper or a controller change of D9's own.
8. **`pnpm lint` is not run** (consistency pass): the repository has no ESLint configuration (`docs/development.md` §4; D-env's Global Constraints), so `eslint --fix` fails; the checks before a commit and at the end are `pnpm format`, `pnpm build`, `pnpm test` and the `test:e2e` suites.
