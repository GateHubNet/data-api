# MPTokens: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Full MPToken support:
- issuances and holders;
- MPT amounts in payments, balance changes and escrows;
- MPT payment volume;
- per-issuance stats and routes.

**Architecture:**
- MPT amounts use the existing `(currency, issuer)` representation, with `currency` = the 48-hex issuance id. The payment and balance-change parsers learn MPT.
- A new `mpt.parser.ts` writes issuance events and holder states into three ledger tables.
- The aggregator rebuilds `mpt_issuances`, `mpt_holders` (+ by-amount) and `mpt_daily`.
- New `/v2/mpt/...` and account routes serve it.

**Tech Stack:** as in `2026-10-17-amm-data.md`.

**Spec:** `docs/superpowers/specs/2026-10-17-mpt-data-design.md`; shared rules in `2026-10-17-amendments-roadmap.md`. **Depends on:** the NFT plan, completed.

## Global Constraints

Identical to `docs/superpowers/plans/2026-10-17-amm-data.md` → Global Constraints. In addition:
- **Branch:** `feat/mpt-data`, cut from the finished `feat/nft-data`. `PARSER_VERSION` = 4.
- **Issuance ids:** an id is exactly 48 hex characters and decodes to (sequence, issuer). Anything else gives 400 `invalid mpt issuance id`.
- **Amounts:** MPT amounts are never scaled in storage or responses. Scaling by `asset_scale` happens only when a value is converted to a Float64 shadow for aggregation, and `*_f` columns store the scaled value.

## Review Focus

1. **A payment between holders of an issuance with a `TransferFee`.** The delivered amount, the holder deltas and the issuer's `OutstandingAmount` delta must reconcile: the fee is burned back to the issuer. Owner: Task 3.
2. **An escrowed MPT.** `LockedAmount` moves, and the holder's spendable `MPTAmount` decreases at create and returns at cancel. The balance-change rows must show escrow types, not a payment. Owner: Task 3.
3. **An issuance with more than 100k holders.** `mpt_holders_by_amount` is rebuilt over several ticks without a half-written set ever being visible to readers. Owner: Task 6.
4. **A request mixing MPT and IOU syntax.** `/v2/payments/<48hex>+<wrong issuer>` gives 400 `issuer does not match mpt issuance`, and a 40-hex currency is still an IOU. Owner: Task 5.
5. **An existing parity test.** Ripple-mock data has no MPTs, so all existing payment and balance-change parity tests must stay byte-identical. Owner: Tasks 3 and 5.
