# NFTs and URITokens Data (D3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ingest XRPL NFTokens and Xahau URITokens into five ledger tables under a new parser version, keep the state of every NFT, holdings, collections, collection holders and an `nft_volume` metric current in the aggregator, and serve `/v2/nfts/{id}[/history|/offers]`, `/v2/nft_collections[…]`, `/v2/nft_sales`, `/v2/accounts/{address}/nfts|nft_history` and `/v2/network/nft_volume`, each with the program's `coverage`; and build the program's one coverage service.

**Architecture:** One pure parser (`nft.parser.ts`) turns each successful transaction's `NFTokenPage`, `NFTokenOffer` and `URIToken` diffs into events, which `buildLedgerRows` writes into `nft_events` and four copies of it (by account, by collection, the sales, the touches), all created by migration 011. A pure fold (`foldNftEvents`) gives an NFT's state from its events; two aggregator jobs (`nft_state` every tick, `nft_collections` every fifth) write the version-set tables `nfts`, `account_nfts`, `nft_collections` and `nft_collection_holders`, and the volume jobs gain the metric `nft_volume`. One SQL (`nftSalesNativeSql`) converts prices to the native currency at D2's daily rates for every reader. The API module `apps/api/src/nft/` serves the routes on the contract layer; `FeatureCoverageService` (new, shared by D5, D6, D7 and D9) answers `coverage` from the parser versions in `ledgers` and the amendments data.

**Tech Stack:** TypeScript (strict), NestJS 10, ClickHouse 26.8 (`@clickhouse/client`), pnpm 10 workspace, jest + ts-jest, testcontainers, supertest, `bignumber.js`, `ripple-address-codec`, `ripple-binary-codec` 2.x.

**Spec:** `docs/superpowers/specs/2026-10-17-nft-data-design.md` (revised 2026-10-24; cited "spec §n" and "decision n"). The roadmap's shared rules (`2026-10-17-amendments-roadmap.md`) stay binding. The explorer side is x-explorer `docs/superpowers/specs/2026-10-24-nft-pages-design.md` (E8), built after this plan from its API description. This plan replaces the plan of the spec's 2026-10-17 version, which was never executed.

**Branch:** `feat/explorer-data-2` in `/Users/golobitch/github.com/GateHubNet/data-api-worktrees/explorer-data-2` (stacked on the owner's PR #20). D-env (`docs/superpowers/plans/2026-10-24-testnet-profiles.md`) is built on this branch before Task 1. All work is committed here and never pushed.

## Review Focus

1. **A page split or merge in the transaction that mints, moves or burns an NFT.** Ids are compared over the union of all `NFTokenPage` nodes of the transaction, so an NFT that only changed page is no event. A mint next to a split is one `mint`, never a `burn` plus a `mint`. Pinned by Task 4's `page_split_with_mint` case and `it('an NFT that only moves to another page of its owner is no event')`, and by Task 6's union invariant.
2. **An NFT minted before the coverage start.** Its first indexed event is a sale, a transfer or an offer. The fold names the owner that a sale or transfer gave it (and the seller as a past owner); an offers-only NFT has no `owner`; `minted` is absent; the detail answers 200 (not 404) with the NFT's own `complete: false`. Pinned by Task 8's `it('folds an NFT whose mint is not indexed')` and Task 12's `it('serves an NFT whose mint is not indexed, with its own coverage incomplete')`.
3. **A sale priced in an issued currency with no daily rate that day** (or in a 40-hex currency code). It counts in `sale_count`, `sales_count` and the volume row's `count`, but not in `volume_native`, the component, `avg_price_native` or `min_price_native`, and its `converted_amount` is absent. Pinned by Task 10's `it('leaves a sale without a rate out of the components but in the row count')`, Task 11's `it('counts an unrated sale in sales_count and not in volume_native')` and Task 13's `it('stats: … a day whose only sale has no rate has sales_count 1 and no price fields')`.
4. **A URIToken burned and minted again by the same issuer with the same URI** (one id, decision 19). The state follows the newest events: the owner is set again, `burned` is false, `minted` is the newest mint; holdings move; the history keeps both lives. Pinned by Task 5's `it('a burn and a re-mint of the same id are two lives of one URIToken')` and Task 8's `it('a re-mint after a burn gives the NFT an owner again')`.
5. **Coverage on a testnet, at Xahau's genesis, and with no stored ledger.** A testnet profile answers `complete: false` when there is no indexed `EnableAmendment` (the metadata file's enable ledger is dropped there) and for a feature without an amendment (it has no `firstLedger`). Xahau's `URIToken` starts at ledger 1. An empty database answers `{ "complete": false }`. Pinned by the named cases of Task 3's `feature-coverage.service.spec.ts`.

The rules (spec §2.1–2.3, §2.5, §2.6):
- **Which transactions:** successful ones only (`meta.TransactionResult === 'tesSUCCESS'`).
- **Ids and owners:** ids come from the union of all `NFTokenPage` nodes. The "before" ids are the `PreviousFields.NFTokens` of a modified page and a deleted page's `FinalFields`; a created page has none. The "after" ids are `FinalFields`/`NewFields` of modified and created pages. The owner of an id is `pageOwner` of the page that holds it. Then apply the table of §2.1.
- **Mints:** issuer, taxon, serial, flags and fee come from `decodeNFTokenId`; `uri` from the page's `NFToken.URI`.
- **Expiration:** `Expiration + 946684800`.
- **Sales:** a sale's `offer_id` and `is_sell_offer` are the accepted offer's (direct) or the sell offer's (brokered, Ruling 14). Its `royalty_est` is `(price − broker_fee) × transfer_fee / 100000`, rounded down to whole drops for the native currency and to 16 significant digits for an issued one (Ruling 13); it is `''` when the fee is 0 or the issuer is the seller or the buyer.
- **Roles:** `rolesOf` follows spec §2.6: `issuer` only on a mint, a burn or a sale; `minter` for the sender of a mint who is not the issuer; `offer_owner` for the owner of a created, cancelled or removed offer (an offer event's `account`).
- **Order** (Ruling 2): offer cancels and removals in `AffectedNodes` order; then mints, sales, transfers, burns and modifies, in that order of kind and by `nft_id` within a kind; then offer creations in `AffectedNodes` order. `event_index` counts from 0.
- **Skips:** an MPT `Amount` skips that event and counts it in `skipped`.
- **Inputs** are never written to.

The unscrambling multiplies two 32-bit values: compute it exactly (`Math.imul(384160001, serial) + 2459 >>> 0`, or with `BigInt`). A `Number` product exceeds 2^53 for serials above about 23 million.

The fold (spec §3.1):
- The owner comes from the newest `mint`, `sale` or `transfer`; a `burn` clears it, and a later `mint` sets it again.
- `uri` comes from the newest `mint` or `modify`.
- `minted` is the newest mint. `burned` and `burned_at` hold only while the newest ownership event is a `burn`.
- `sale_count` counts all sales; `last_sale` is the newest sale.
- Offer events count only for `first_ledger` and `last_ledger`.
- `owners` are the non-empty `to_account` of mints, sales and transfers, and the `from_account` of sales, transfers and burns.

The functions:
- `nftStateWatermark` and `nftsChangedSince` have the contracts of `ammPoolsWatermark` and `poolsChangedSince` (`amm-pools.job.ts`), with `nft_touches` for `amm_pool_touches`, the newest `nfts.last_ledger` of each NFT for the pool's `last_ledger`, and NFTs for pools.
- `nftsInLedgers` gives the NFTs with a touch in `[from, to]`, plus those whose newest `nfts` row has its `first_ledger` or `last_ledger` there.
- `rebuildNfts` reads the NFTs' `nft_events` (`nft_id IN …`, capped at the committed head, in key order, `LIMIT 1 BY ledger_index, tx_index, event_index`) and folds each. It writes under one version per batch (the ClickHouse clock in ms, above the batch keys' newest): one `nfts` row per NFT, and one `account_nfts` row per account of `owners` (`held` 1 for `owner`, else 0). For an NFT with no event left, it runs a lightweight `DELETE` of its `nfts` rows and writes a `held = 0` row for each owner of its newest `account_nfts` rows. `collections` are the distinct keys of what it wrote or removed. Nothing is written once `signal` is aborted (`NftRebuildAborted`).

The conversion (spec §3.3, Ruling 9) is one SQL for every reader:

```sql
-- 1. the asset-days to ask for (rates.rateRowsSql of these)
SELECT DISTINCT currency, amount_issuer, toString(toDate(close_time, 'UTC')) AS day_text FROM (<sales>) WHERE amount_issuer != ''
-- 2. the answer
SELECT s.*,
       if(s.amount_issuer = '', toDecimal128OrNull(s.amount, 6),
          if(r.rate_f > 0, toDecimal128(round(s.amount_f / r.rate_f, 6), 6), NULL)) AS converted_native,
       toFloat64OrNull(toString(converted_native)) AS converted_native_f

    ON s.currency = r.currency AND s.amount_issuer = r.issuer AND toDate(s.close_time, 'UTC') = r.day

SELECT * EXCEPT newest_page_read, newest_page_read FROM (
  SELECT *, count() OVER () AS newest_page_read
    FROM (SELECT <columns>, version FROM <table> WHERE <where> ORDER BY <key ASC|DESC>, version DESC LIMIT {newest_page_cap:UInt32})
   ORDER BY <key ASC|DESC>, version DESC
   LIMIT 1 BY <key>)
 WHERE <keep>
 ORDER BY <key ASC|DESC>
 LIMIT {newest_page_limit:UInt32}
```

## Rulings

1. **`account_nft_events` names the event's actor `actor`.** Its key column `account` is the account the row is for (spec §1.1's `ORDER BY (account, …)`), which would collide with `nft_events.account` (who did it). Readers serve `actor` as the event's `account`.
2. **Event order inside the ownership group** (spec §2.5, "mints, sales, transfers, burns and modifies (by `nft_id`)"): by kind in that order, then by `nft_id` within a kind.
3. **Xahau's `firstLedger` is 1**, and `URIToken`'s enable ledger in `xahau.json` is `{ "ledger_index": 1, "date": "2023-10-30" }`. `complete_ledgers` of `xahau.network` starts at 1 (2026-10-24); ledger 1 is the genesis (close time 0, zero parent hash) and has `URIToken` in its `Amendments`. The date is that of ledger 2, the first closed ledger, since ledger 1's close time is the epoch. Complete coverage on Xahau therefore needs ledger 1 indexed (`--from 1`).
4. **Coverage features are registered by name** in `COVERAGE_FEATURES` (`apps/api/src/common/coverage-features.ts`), each as `{ parserVersion, startOf(profile): FeatureStart }`. So D5's and D7's `coverage('escrows')`, and a profile flag (`hasDelegation`, `hasMpt`) choosing `unavailable`, are one mechanism. Later sub-projects add entries; they change no rule.
5. **Per-item `complete`** (spec §4, "its `minted` ledger is at or above `from_ledger_index`"): the item's first indexed event must be its creation (a mint), at or above `from_ledger_index`. `NftFold.created_ledger` carries it. D5 applies the same rule to an object's creation.
6. **A failed coverage read fails the route** with the route's own 500 message: no `complete: false` is invented and kept for 60 s.
7. **`/stats` without `start` is 400 `start is required`**, the API's wording for a missing required parameter (`issuer is required`, `family is required`).
8. **`/v2/nft_sales?currency=USD+r…`**: in a query string a raw `+` arrives as a space, so both `%2B` and the space separate the currency from its issuer.
9. **Converted prices are `Decimal(38, 6)`**: a native price exactly, an issued one as `round(amount_f / rate_f, 6)` (the rate is a Float64). Sums over those values are exact; the text has no trailing zeros and no exponent.
10. **`is_sell_offer` is a JSON boolean** in `NftEvent` and `NftOffer` (the column is a `UInt8`).
11. **`nft_volume`'s row `count` is the sentinel's** (every sale of the window), not the sum of the components (the rated sales); `toVolumeRow` branches on the metric.
12. **The collection routes are two controllers.** `NftCollectionListsController` (every sub-route, both key forms) is registered before `NftCollectionsController`, so `/:issuer/nfts` is never read as a taxon; `nft.module.spec.ts` pins this, as `amm.module.spec.ts` does for AMM.
13. **The royalty estimate of an issued price** is rounded down to 16 significant digits (a native one down to whole drops, as the spec says).
14. **A sale's `offer_id`** is the accepted offer's (direct, with its side) or the sell offer's (brokered, `is_sell_offer` 1).
15. **`first_mint_*` are nullable**, like `last_mint_*`: a collection whose mints all came before the coverage start has neither.
16. **The `nft_state` hook runs with or without the `aggregates` option**: `hooksOfSlice` runs the hooks of the runners that exist.
17. **Tick order**: `nft_state` right after `amm_pools` (spec §3.1); `nft_collections` after `amm_daily`, beside the other every-fifth-tick job, so that the jobs that must be fresh at each tick keep their places.
18. **One parser for both networks**: `NftParser` acts on `NFTokenPage` and `NFTokenOffer` nodes or on `URIToken` nodes, so it needs no network (parsers know none, D-env §3).
19. **ADR-0010's amendment numbers run in build order** (consistency pass): D3 takes Amendment 5 after PR #20's 4, then D4 6, D5 7, D6 8, D7 9, D8 10, D9 11, each checked at build time.
20. **`pnpm lint` is not run** (consistency pass): the repository has no ESLint configuration (`docs/development.md` §4; D-env's Global Constraints), so `eslint --fix` fails; the checks before a commit and at the end are `pnpm format`, `pnpm build`, `pnpm test` and the `test:e2e` suites.
