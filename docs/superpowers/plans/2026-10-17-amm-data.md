# AMM data: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ingest, store and serve XRPL AMM activity:
- swaps counted as exchanges;
- pools and pool history;
- liquidity events;
- votes and bids;
- AMM volume and daily pool stats.

**Architecture:**
- A new pure `amm.parser.ts` plugs into `buildLedgerRows`.
  - It writes AMM swaps into the existing `exchanges` / `account_exchanges` tables (new `amm_account` column).
  - It writes pool states, liquidity events and governance rows into four new ledger tables.
- The syncer's aggregator rebuilds current pools (`amm_pools`) and per-pool daily stats (`amm_daily`) from those tables, and adds an `amm_volume` metric to the volume sets.
- New `/v2/amm/...`, account and network routes serve all of it with the existing Ripple contract layer.

**Tech Stack:** NestJS 10, TypeScript, ClickHouse 26.8.14.3 (`@clickhouse/client`), xrpl.js 2.14 / ripple-binary-codec 2.x, Jest, testcontainers, pnpm workspace (`apps/api`, `apps/syncer`, `packages/shared`).

**Spec:** `docs/superpowers/specs/2026-10-17-amm-data-design.md`. The spec builds on `docs/superpowers/specs/2026-10-15-ripple-dropin-design.md`, and its rulings are in `docs/superpowers/plans/2026-10-15-ripple-dropin.rulings.md`, which stays binding.

## Global Constraints

**Platform and versions**
- Node ≥ 20.19.
- ClickHouse is pinned to `26.8.14.3`; tests use the shared testcontainers helper.
- Import `@gatehub/toolbox` only via `@gatehub/toolbox/lib/<module>` subpaths.

**SQL and ClickHouse**
- Every table name comes from `${Table.X}`. Every value is bound as `{name:Type}`. `apps/api/src/common/sql-tables.spec.ts` enforces both.
- No FINAL on list reads. Every paged range read goes through `readDistinctPage` (inner plain `ORDER BY <full key> LIMIT`, dedupe outside, R106). Each new paged read gets an EXPLAIN and a `system.query_log.read_rows` bound test (pattern: `apps/api/test/support/read-rows.ts`).
- Inserts go through `ClickHouseService.insert` (`async_insert: 0`). New ledger tables get `non_replicated_deduplication_window = 1000` and must be added to every place that lists ledger tables: `CHILD_TABLES` (`build-rows.ts`), `LEDGER_KEYED_TABLES` (`ingest-state.ts`), and any test that counts them.
- `DateTime64` values are sent as fractional unix seconds, never ms integers.

**Data formats**
- Exact amounts are `String`; `*_f Float64` shadows are used only for aggregation.
- Rates use `precision8`. Times use `fmtTime`. Undefined keys are omitted. `Object.keys` order of every new object is pinned by a test.

**API conventions**
- Controllers use `@RippleController` and `@RippleRoute('<500 message>')`, plus `import type { Request, Response } from 'express'`.
- Every list sets the `Link` header (JSON and CSV), uses `limitParam({def: 200, max: 1000})` and supports `format=csv` via `@Csv`.
- Unknown params are ignored.

**Tests**
- Duplicate-row tests store a real duplicate: `SYSTEM STOP MERGES`, a separate insert with `insert_deduplicate: 0`, then assert that `count()` doubled.
- e2e page walks use the harness's persistent `h.api()` client.
- TDD: spec first, run RED, implement, run GREEN. Test output must be pristine.

**Safety and commits**
- Never read `apps/*/.env`, `deploy/.env.prod` or npm credentials.
- Delete only files you created, inside your own scratch folder. Never `rm -rf` a computed, parent or shared temp path.
- Public nodes are used with at most 2 requests in flight, and you stop on a rate-limit answer. Use `wss://s2.ripple.com` for XRPL.
- Commit on `feat/amm-data`. The message ends with the Co-Authored-By trailer of the model writing the code.

## Review Focus

1. **A swap through an IOU/IOU pool whose `AccountRoot` is not in the metadata.** It must still be found. If it can't be found, it must be counted (`syncer_amm_unclassified_total`), never silently dropped. Owner: Task 3 (test with the recorded IOU/IOU fixture, plus a synthetic metadata that drops the pool `AccountRoot` while keeping the `AMM` node).
2. **A pool deleted and later re-created for the same pair, with a new pool account.**
   - The pair form `/v2/amm/pools/:base/:counter` resolves to the live pool, falling back to the most recently deleted one.
   - History, liquidity and swaps stay per account.
   - Owner: Task 9 (synthetic two-pool test).
3. **An issuer with a transfer fee (`TransferRate`).** The pool's IOU delta differs from the taker's. The exchange row must use the pool's deltas, the maker side, as order-book rows use the offer's. Owner: Task 3 (synthetic transfer-rate case asserting the amounts).
4. **A failed (`tec*`) transaction that touches pool nodes, for example by fee threading.** It must produce no swap, no liquidity event and no governance row. It may produce a state row only if a reserve actually changed, which it cannot under `tec`. So it produces nothing. Owner: Task 3.
5. **An `amm=only` page over a pair with heavy order-book traffic and few AMM swaps.** It must stay bounded: the filter has to be inside the inner capped read, not applied after it. Owner: Task 5 (read_rows test with 100k order-book rows and 10 AMM rows).
