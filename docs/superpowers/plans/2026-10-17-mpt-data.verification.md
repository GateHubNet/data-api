## Incident: migrations applied to data-api-new-clickhouse-1

**What happened.** The first migrate command of the check, in zsh:

```bash
ENVV="PATH=$PATH GH_ENV=container NODE_ENV=production GH_NETWORK=xrpl GH_CLICKHOUSE_URL=http://127.0.0.1:28123 GH_CLICKHOUSE_USER=default GH_CLICKHOUSE_PASSWORD="
env -i $ENVV pnpm --filter @gatehub/data-api-shared ch:migrate
env -i $ENVV pnpm --filter @gatehub/data-api-shared ch:migrate shared
```

zsh does not split an unquoted variable, so `env` received one long `PATH` and `GH_CLICKHOUSE_URL` was never set. The code's default, `http://localhost:8123`, was used, and `data-api-new-clickhouse-1` publishes that port. The dispatch said never to touch that container.

**What it did**, from the runner's output (`live/migrate.log`, `live/migrate-shared.log`):

| Database | Result | Statements |
| --- | --- | --- |
| `xrpl` | `applied=3 skipped=14` | `015_supply.sql`: `CREATE TABLE IF NOT EXISTS` of `genesis_mints`, `imports`, `reward_claims`, `network_supply`. `016_validator_toml_details.sql`: `ALTER TABLE validator_domains ADD COLUMN IF NOT EXISTS` of `owner_country`, `server_country`, `toml_network`, `toml_unl`, `toml_version`. `017_mpt.sql`: `CREATE TABLE IF NOT EXISTS` of the seven MPT tables. Three rows in `schema_migrations`. |
| `shared` | `applied=0 skipped=2` | No schema change: the runner read `schema_migrations`. |

**How it is known.** The scratch server had no `xrpl` database after those commands (`SHOW DATABASES`, read at the time and not stored), and the runner reported 14 files already applied, so it was another server. That server's contents were not read afterwards, so everything above comes from the runner's log.

**What it means.**

- All of it is additive, and the new tables are empty unless something writes to them. 016's own header says code from before that release neither reads nor writes its columns. That was read from the file; the images running in that stack were not inspected.
- The listing of the containers is the same before and after, apart from its timestamp line, and all five were still up. It has no health column. The two syncers are `unhealthy`, and that is not from this: the program's handoff (`.superpowers/handoffs/2026-10-31-continue-here.md` of the `data-api` checkout), written before this check, already records it.
- **The stack's next deploy** skips these three files if they are unchanged. The runner checksums applied files and refuses one that changed, so **a fix wave that edits `017_mpt.sql` would make `migrate-xrpl` fail on that stack** until its row is dealt with.

**Decided (owner, 2026-10-31): leave it.** No revert was made. The next deploy of that stack skips the three files as long as they do not change.

For the record, undoing it would mean, on that server: drop the eleven tables above, drop the five columns of `validator_domains`, and delete the three files' rows from `xrpl.schema_migrations`.

**From then on** every process of the check started from a script with `env -i`, the scratch URL named in an argument array, and a check that the published port belongs to the scratch project. The scratch migration then reported `applied=17 skipped=0` and `applied=2 skipped=0`, and `xrpl` held 86 tables (read at the time and not stored), 85 and `schema_migrations`, as Task 3's count says.

## The live check: not done

**Setup.** Compose project `d9mptlivecheck`, one ClickHouse `26.8.14.3` on `127.0.0.1:28123`, no env file and no named volume. The ranges were three of 100 ledgers around recorded activity:

| Range | Recorded cases in it |
| --- | --- |
| 105827835..105827934 | `authorize_holder`, `authorize_by_issuer`, `payment_mint` |
| 107211700..107211799 | `escrow_create`, `escrow_finish`, `issuance_set_lock_holder`, `issuance_set_unlock_holder` |
| 107541330..107541429 | `clawback_partial` |

```bash
node apps/syncer/dist/cli/range-ingest.js --from 105827835 --to 105827934 --concurrency 1 --run-id d9-live-105827835
# GH_NODE_ENDPOINTS=ws://127.0.0.1:23110, a throwaway proxy to wss://s2.ripple.com only
```

**One request in flight.** `--concurrency 1` alone does not hold it, since xrpl.js sends a `ping` every 30 s. So everything went through a throwaway proxy with a queue: one request at a time, 3 s between an answer and the next request (the delay Task 1's recording ended on), heartbeats answered locally (11 of them, none reached the node), and forwarding stopped at the first rate-limit answer.

**What the node answered.**

| | |
| --- | --- |
| Requests sent to s2 | 67: `server_info` 1, `ledger` 66 (105827835 to 105827900) |
| Time | 20:30:38Z to 20:36:18Z, mean 2,150 ms a ledger, largest answer 296,007 bytes |
| Stop | Request 67, ledger 105827900: the answer carried `warning: load` |
| Ledgers committed | 0: the range is one chunk, and a chunk is written whole, so the 66 fetched ledgers were lost |

`warning: load` is the server warning a client that it is near its limit, not a refusal, and that ledger's answer was complete. It was treated as a rate-limit answer because going on after it risks the machine's access to the node. Nothing was resumed.

**After the stop.** No request left the machine: the last one to reach s2 was at 20:36:18.029Z, and the proxy refused the 7 that followed. The CLI itself kept retrying against the proxy, because the script's `kill` reached a subshell and not node: the last retry in `proxy.jsonl` and `range-ingest.log` is at 20:36:49Z. It was then killed by its PID, at 20:37:14Z (read at the time and not stored).
